Grow a B+ tree

Each box holds at most three keys. Insert a fourth and the box splits in two, pushing a key up to its parent. That keeps the tree short and every search just a few hops long. The bottom row is linked left to right, so range scans simply walk along it.

The engine I built supports full CRUD with disk storage, plus schema validation: NOT NULL, UNIQUE, CHECK and foreign keys. Try inserting a duplicate.

This demo is a real B+ tree running in your browser. Order 4 keeps the splits easy to see.

The coffee-spill test

A database has to survive a crash at the worst moment. The rule of write-ahead logging is simple: write what you're about to do in a diary first, then do it.

After a crash, recovery re-reads the diary. Committed transactions are redone, and half-finished ones are thrown away, so the data is never left half-written. My transaction manager enforced all four ACID properties on top of that log.

Olympia: sports management, sharded

Olympia is a full web app for running sports events. When one table gets big, hash-based sharding spreads its rows across several: hash the key, take the remainder, and that's your filing cabinet. There's no lookup table and the load stays even.

  • JWT authentication, role-based access control and session management
  • Benchmarked API endpoints with EXPLAIN, then fixed slow queries with indexes
  • Sharding across multiple tables for horizontal scalability
